## Методология

**Подход:** Эмпатическое проектирование (Design Thinking) — анализ интерфейсов и процессов с позиции конечного пользователя.

**Роли:**
1. **Клиент** — заказывает еду через Web (Next.js) и/или Mobile (Flutter)
2. **Курьер** — доставляет заказы через Mobile (Flutter, Android)
3. **Оператор** — обрабатывает заказы через CRM (Web) и/или Operator App (Electron)
4. **Администратор** — управляет системой через CRM (Web)

**Фокус анализа:**
- Неудобства интерфейсов
- Лишние действия пользователей
- Сложные сценарии
- Слабые места в процессе заказа
- Потенциальные жалобы пользователей

**Шкала критичности:**

| Уровень | Описание | Влияние на бизнес |
|---------|----------|-------------------|
| 🔴 **Критично** | Пользователь не может выполнить задачу | Потеря заказов, отток |
| 🟡 **Важно** | Пользователь может выполнить задачу, но с трудом | Снижение конверсии, NPS |
| 🟢 **Желательно** | Можно улучшить, но не блокирует | Долгосрочное улучшение UX |

# 1. Клиент (Client)

## 1.1 Профиль пользователя

**Характеристики:**
- Возраст: 18-45 лет
- Устройства: Mobile (60%), Desktop (30%), Tablet (10%)
- Цель: быстро заказать еду с доставкой или самовывозом
- Ожидания: 2-5 минут от входа до оформления заказа
- Техническая грамотность: средняя

**Ключевые сценарии:**
1. Первый заказ (регистрация → выбор блюд → оплата → отслеживание)
2. Повторный заказ (вход → повтор прошлого заказа)
3. Заказ компании (большая сумма, несколько персон)
4. Предзаказ (заказ на определённое время)

## 1.2 Неудобства интерфейсов

### 🔴 К1.1. Phone OTP приходит на email вместо SMS

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент вводит номер телефона, ожидает SMS с кодом. |
| **Текущее поведение** | Код отправляется на email, привязанный к номеру. |
| **Ожидание пользователя** | SMS с кодом (как у всех сервисов). |
| **Проблема** | Пользователь не понимает, куда пришёл код. Проверяет SMS — пусто. Проверяет email — есть, но не всегда сразу. Думает, что это спам. |
| **Влияние** | **Конверсия -30%.** До 30% пользователей бросают регистрацию. |
| **Цитата пользователя** | «Я ввёл телефон, а код почему-то на почту. Это нормально?» |
| **Решение** | Интеграция SMS.ru (P0-3 в roadmap, 16-24ч). |

### 🔴 К1.2. Платёжный шлюз не работает

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент выбирает «Онлайн» в способах оплаты. |
| **Текущее поведение** | Опция «Онлайн» — просто строка в enum, нет интеграции со шлюзом. |
| **Проблема** | Клиент видит опцию, нажимает, ничего не происходит. Или деньги списываются, но заказ не создаётся. |
| **Влияние** | **Revenue loss 100%** онлайн-заказов. Клиенты уходят к конкурентам. |
| **Цитата пользователя** | «Оплатил, а заказа нет. Где деньги?» |
| **Решение** | Интеграция YooKassa / CloudPayments (P0-2 в roadmap, 40-60ч). |

### 🔴 К1.3. Меню не синхронизировано с сервером

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент открывает `/menu` на Web. |
| **Текущее поведение** | Используется локальный `lib/catalog.ts`, а не API `/api/v1/categories`. |
| **Проблема** | Клиент видит старое меню. Заказывает блюдо, которого нет в наличии. Или видит старую цену, а в чеке — новая. |
| **Влияние** | **Жалобы в поддержку.** Возвраты. Потеря доверия. |
| **Цитата пользователя** | «Заказал борщ за 350₽, а с меня списали 450₽. Почему?» |
| **Решение** | `/menu` на API (P0-12 в roadmap, 4-6ч). |

### 🟡 К1.4. Адрес в About — «г. Москва»

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент открывает «О ресторане» в мобильном приложении. |
| **Текущее поведение** | Видит «г. Москва, ул. Кондитерская, д. 15». |
| **Проблема** | Ресторан находится в Омске. Клиент думает, что ошибся приложением. |
| **Влияние** | **Потеря доверия.** Клиент уходит. |
| **Решение** | P0-15 в roadmap, 1ч. |

### 🟡 К1.5. `/social/tg` — 404

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент нажимает на ссылку «Telegram» в футере. |
| **Текущее поведение** | «Страница не найдена». |
| **Проблема** | Нет case для `tg` в switch-case. |
| **Влияние** | **Мелкий баг**, но снижает доверие. |
| **Решение** | P0-14 в roadmap, 1ч. |

### 🟡 К1.6. Долгая загрузка страниц (LCP > 3с)

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент открывает `/` или `/menu` на медленном интернете. |
| **Текущее поведение** | Все 38 `.tsx` файлов — `'use client'`. RSC не используется. |
| **Проблема** | HTML загружается только после JS. На 3G — 5-10 секунд. |
| **Влияние** | **Конверсия -20%** (исследование Google: +1с загрузки = -20% конверсии). |
| **Решение** | SSR для публичных страниц (P1-4 в roadmap, 20-30ч). |

### 🟢 К1.7. Нет «Избранного»

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент хочет повторно заказать любимое блюдо. |
| **Проблема** | Нет функции «Добавить в избранное». Клиент ищет вручную. |
| **Влияние** | **Снижение повторных заказов.** |
| **Решение** | Добавить избранное (P4, не в roadmap, 16-24ч). |

### 🟢 К1.8. Нет отслеживания заказа в реальном времени

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент хочет узнать, где курьер. |
| **Проблема** | Нет карты с курьером. Только текстовые статусы. |
| **Влияние** | **Звонки в поддержку:** «Где мой заказ?» |
| **Решение** | Карта с курьером (P4, 30-40ч). |

## 1.3 Лишние действия пользователей

### 🔴 К1.9. Регистрация по email + phone + OTP

| Параметр | Описание |
|----------|----------|
| **Текущий процесс** | Email → пароль → имя → phone → OTP → готово. 5 шагов. |
| **Оптимальный процесс** | Phone → SMS-код → имя → готово. 3 шага. |
| **Проблема** | Двойная аутентификация (email + phone) замедляет регистрацию. |
| **Влияние** | **Конверсия -15%** на этапе регистрации. |
| **Решение** | Упростить регистрацию (P3, 8-12ч). |

### 🟡 К1.10. Обязательный email при заказе

| Параметр | Описание |
|----------|----------|
| **Текущий процесс** | При оформлении заказа требуется email. |
| **Проблема** | Многие пользователи не хотят оставлять email. |
| **Влияние** | **Брошенные корзины** на этапе оформления. |
| **Решение** | Сделать email опциональным (P3, 2-4ч). |

### 🟡 К1.11. Нет повтора прошлого заказа

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент хочет повторить вчерашний заказ. |
| **Текущее поведение** | Нет кнопки «Повторить заказ». Нужно вручную добавлять из меню. |
| **Проблема** | 10-15 минут вместо 30 секунд. |
| **Влияние** | **Снижение повторных заказов.** |
| **Решение** | «Повторить заказ» (P3, 4-6ч). |

## 1.4 Сложные сценарии

# 2. Курьер (Courier)

## 2.1 Профиль пользователя

**Характеристики:**
- Возраст: 20-40 лет
- Устройства: Android (100%, iOS не поддерживается)
- Цель: получить заказ → забрать из ресторана → доставить клиенту
- Условия работы: на улице, в движении, часто в перчатках
- Техническая грамотность: средняя-низкая

**Ключевые сценарии:**
1. Начало смены (логин → онлайн → получение заказа)
2. Получение заказа (push → просмотр деталей → принятие)
3. Забор из ресторана (навигация → подтверждение)
4. Доставка клиенту (навигация → контакт с клиентом → подтверждение)
5. Завершение смены

## 2.2 Неудобства интерфейсов

### 🔴 КУ1.1. Нет push-уведомлений о новых заказах

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Оператор назначает курьера на заказ. |
| **Текущее поведение** | Нет push. Курьер должен держать приложение открытым. |
| **Проблема** | Курьер пропускает заказы, пока приложение в фоне. |
| **Влияние** | **Задержки доставки.** Жалобы клиентов. Потеря заказов. |
| **Цитата курьера** | «Я был в туалете, а заказ ушёл другому. Где уведомления?» |
| **Решение** | Push через FCM/RuStore (P0-10 в roadmap, 12-16ч). |

### 🔴 КУ1.2. Навигация не работает

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер нажимает «Построить маршрут». |
| **Текущее поведение** | Snackbar «Функция откроется во внешнем навигаторе». Ничего не происходит. |
| **Проблема** | Курьер не может проложить маршрут. Ищет адрес вручную. |
| **Влияние** | **Задержки доставки 10-15 минут.** Жалобы клиентов. |
| **Цитата курьера** | «Я потерялся. Где этот адрес?» |
| **Решение** | `url_launcher` с deep-link (P0-9 в roadmap, 4-6ч). |

### 🟡 КУ1.3. Нет подтверждения доставки (фото/подпись)

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер доставил заказ. |
| **Текущее поведение** | Просто нажимает «Доставлено». |
| **Проблема** | Клиент говорит «Не получил заказ». Нет доказательств. |
| **Влияние** | **Спорные ситуации.** Потеря денег. |
| **Решение** | Фото у двери / подпись клиента (P3, 8-12ч). |

### 🟡 КУ1.4. Нет оффлайн-режима

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер в зоне плохого покрытия (подвал, лифт). |
| **Проблема** | Приложение не работает без интернета. |
| **Влияние** | **Невозможно обновить статус.** Заказы «зависают». |
| **Решение** | Оффлайн-режим с sync при восстановлении связи (P3, 16-24ч). |

### 🟡 КУ1.5. Нет чата с клиентом

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер не может дозвониться клиенту. |
| **Проблема** | Нет in-app чата. Только телефон. |
| **Влияние** | **Курьер не может уточнить адрес.** Задержки. |
| **Решение** | In-app чат (P3, 20-30ч). |

## 2.3 Лишние действия

### 🟡 КУ1.6. Долгое обновление статуса

| Параметр | Описание |
|----------|----------|
| **Текущий процесс** | Открыть заказ → нажать «В пути» → подтвердить → обновить. 4 шага. |
| **Оптимальный процесс** | Свайп по карточке заказа. 1 шаг. |
| **Влияние** | **10-15 секунд** на каждый заказ. За смену — 5-10 минут. |
| **Решение** | Свайп-жесты (P3, 4-6ч). |

### 🟡 КУ1.7. Нет быстрого доступа к контактам

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер хочет позвонить клиенту. |
| **Текущее поведение** | Открыть заказ → скопировать номер → открыть телефон → вставить. 4 шага. |
| **Оптимальное** | Кнопка «Позвонить» прямо на карточке. 1 шаг. |
| **Влияние** | **20-30 секунд** на каждый звонок. |
| **Решение** | Кнопка «Позвонить» (P3, 2-4ч). |

## 2.4 Сложные сценарии

### 🟡 КУ1.8. Забор из ресторана с несколькими заказами

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер должен забрать 3 заказа из ресторана. |
| **Проблема** | Нет списка заказов для забора. Нужно листать по одному. |
| **Влияние** | **Путаница.** Забытые заказы. |
| **Решение** | Список «К забору» (P3, 4-6ч). |

### 🟡 КУ1.9. Доставка в незнакомый район

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Курьер впервые в этом районе. |
| **Проблема** | Нет карты с отметкой адреса. Только текст. |
| **Влияние** | **Потеря времени** на поиск. |
| **Решение** | Карта с адресом (P3, 8-12ч). |

## 2.5 Слабые места в процессе доставки

### 🔴 КУ1.10. Нет отслеживания геолокации курьера

| Параметр | Описание |
|----------|----------|
| **Сценарий** | Клиент хочет знать, где курьер. |

# 7. Рекомендации

## 7.1 Немедленные действия (P0, 2 недели)

1. **Интегрировать SMS.ru** — клиенты перестанут бросать регистрацию
2. **Подключить платёжный шлюз** — заработает онлайн-оплата
3. **Перевести `/menu` на API** — меню будет актуальным
4. **Добавить push для курьеров** — заказы не будут пропускаться
5. **Реализовать навигацию курьера** — доставка ускорится на 10-15 минут

## 7.2 Краткосрочные улучшения (P1-P2, 1-2 месяца)

1. **Пагинация в CRM** — операторы смогут работать с >1000 заказов
2. **Поиск по заказам** — время обработки звонка -50%
3. **Поиск по заказам в CRM** — время обработки звонка -50%
4. **SSR для публичных страниц** — конверсия +20%
5. **2FA для администраторов** — защита от компрометации

## 7.3 Долгосрочные улучшения (P3, 3+ месяца)

1. **Дашборд аналитики** — данные для принятия решений
2. **Мониторинг + алерты** — проактивное реагирование
3. **Drag-and-drop в CRM** — ускорение работы операторов
4. **In-app чат курьер↔клиент** — снижение звонков
5. **Промокоды и программа лояльности** — увеличение повторных заказов

## 7.4 Стратегические рекомендации

### Рекомендация 1: Сначала P0, потом всё остальное

Без устранения P0-задач (SMS, платежи, меню, push, навигация) запуск невозможен. Эти 5 задач — **must-have**.

### Рекомендация 2: Метрики UX

Внедрить метрики:
- **NPS** (Net Promoter Score) — для всех ролей
- **Conversion Rate** — для клиентов
- **Order Acceptance Time** — для операторов
- **Delivery Time** — для курьеров
- **System Uptime** — для администраторов

### Рекомендация 3: UX-тестирование

До запуска провести:
