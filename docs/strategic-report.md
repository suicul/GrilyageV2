# Стратегический отчёт о состоянии проекта «Грильяж»

> **Тип документа:** Мета-анализ на основе `project-map.md`, `current-state.md`, `AI_CTO.md`, `audit.md`  
> **Аудитория:** CTO, владельцы продукта, технические лиды  
> **Цель:** Целостная оценка проекта, скрытые риски, каскадные эффекты, Go/No-Go решение  
> **Дата:** июнь 2026  
> **Код не изменён**

---

## Executive Summary

**Общая оценка зрелости:** 68% (production-ready при условии устранения 21 критической проблемы)

**Ключевые выводы:**

1. **Проект функционально полный, но не production-ready.** Реализовано ~85% запланированного функционала, но 21 критическая проблема блокирует запуск.

2. **Архитектура sound, но с системными долгами.** Монорепо, dual JWT, event-driven — правильные решения. Но отсутствие shared Dart-кода, cron-задач и очереди email создаёт каскадные риски.

3. **Безопасность — главный блокер.** 7 критических уязвимостей (хардкод-пароли, CSP `unsafe-inline`, CSRF, WebSocket без auth). Утечка репозитория = полный компромет production.

4. **Масштабирование ограничено single-node архитектурой.** При >100 RPS система деградирует. Read replica + load balancer обязательны перед маркетинговыми кампаниями.

5. **UX имеет 2 критических разрыва.** Phone OTP на email (вместо SMS) и отсутствие онлайн-оплаты. Оба снижают конверсию на 30-50%.

**Go/No-Go решение:** **NO-GO** до устранения Фазы 0 (120-180 часов, 4-6 недель).

**Рекомендация:** Запуск в **soft-launch режиме** (ограниченная аудитория, только pickup, без онлайн-оплаты) возможен через 2 недели после устранения топ-5 блокеров.

## 1. Архитектурная оценка

### 1.1. Сильные стороны архитектуры

**A-S1. Монорепо с npm workspaces**
- **Что хорошо:** Единая кодовая база для TypeScript-приложений (api, web, launcher). Общие типы в `packages/shared`. Упрощает рефакторинг и синхронизацию контрактов.
- **Оценка:** 9/10
- **Риск:** Flutter-приложения не интегрированы в монорепо (нет shared Dart-кода).

**A-S2. Dual JWT для разделения доменов**
- **Что хорошо:** Клиенты и персонал — два независимых JWT-домена с отдельными секретами. Компромет клиентского JWT не даёт доступ к CRM.
- **Оценка:** 10/10
- **Риск:** Refresh-токены в `localStorage` (уязвимость к XSS).

**A-S3. Event-driven архитектура**
- **Что хорошо:** Все операции event-driven (создание заказа → push, смена статуса → WebSocket). Нет блокирующих операций.
- **Оценка:** 8/10
- **Риск:** Нет cron-задач для периодических операций (очистка OTP, деактивация акций).

**A-S4. Prisma как single source of truth**
- **Что хорошо:** Все изменения схемы через `schema.prisma` + миграции. Нет ручных SQL-запросов. Seed-данные версионированы.
- **Оценка:** 9/10
- **Риск:** N+1 запросы в некоторых сервисах (не оптимизированы `include`/`select`).

**A-S5. WebSocket для realtime**
- **Что хорошо:** 5 gateway'ев для разных доменов (staff, orders, mobile, chat, calls). Socket.IO с auto-reconnect.
- **Оценка:** 8/10
- **Риск:** 3 из 5 gateway'ев без аутентификации на connect.

### 1.2. Архитектурные слабости

**A-W1. Отсутствие shared Dart-кода (критично)**
- **Суть:** `apps/mobile/` и `apps/courier/` дублируют ApiClient, Order model, AuthNotifier, темы.
- **Каскадный эффект:**
  - Баг-фиксы требуют двойной работы
  - Статусы заказов рассинхронизированы (mobile: `pending/confirmed/preparing`, courier: `NEW/CONFIRMED/COOKING`)
  - Рефакторинг API требует обновления в двух местах
- **Оценка:** 3/10
- **Стоимость исправления:** 20-30 часов

**A-W2. Single-node инфраструктура (критично)**
- **Суть:** Один VPS, один postgres, один api, один web. Нет репликации, нет load balancing.
- **Каскадный эффект:**
  - Single point of failure → полный downtime при падении VPS
  - Нет возможности maintenance без downtime
  - Масштабирование только vertical (дорого, ограничено)
- **Оценка:** 4/10
- **Стоимость исправления:** 40-60 часов

**A-W3. Отсутствие очереди для email (важно)**
- **Суть:** Nodemailer отправляет письма синхронно. При сбое SMTP — письмо теряется.
- **Каскадный эффект:**
  - Потерянные verification emails → пользователи не могут завершить регистрацию
  - Потерянные order confirmations → клиенты не уверены в заказе
  - Нет retry-логики → повторная отправка требует ручного вмешательства
- **Оценка:** 5/10
- **Стоимость исправления:** 12-16 часов

**A-W4. Все страницы `'use client'` (важно)**
- **Суть:** Все 38 `.tsx` файлов начинаются с `'use client'`. React Server Components не используются.
- **Каскадный эффект:**
  - Плохой SEO (Google не индексирует клиентский JS)
  - Медленная загрузка на слабых устройствах (весь JS выполняется на клиенте)
  - Потеря преимуществ Next.js 16 (streaming, partial prerendering)
- **Оценка:** 6/10
- **Стоимость исправления:** 20-30 часов

**A-W5. Dev ≠ Prod compose divergence (желательно)**
- **Суть:** Разные TLS-режимы, rate-limiting, мониторинг, Redis. Dev: HTTPS. Prod: HTTP-only.
- **Каскадный эффект:**
  - «Работает на dev, падает на prod»
  - Трудно воспроизвести production-баги локально
  - Onboarding новых разработчиков замедлен
- **Оценка:** 7/10
- **Стоимость исправления:** 8-12 часов

### 1.3. Архитектурные решения под вопросом

**A-Q1. Операторское ПО на Electron**
- **Вопрос:** Зачем отдельное Electron-приложение, если есть web CRM (`/admin`)?
- **Анализ:**
  - Дублирует функционал web CRM
  - Single-file HTML (неподдерживаемо)
  - Звонок = `alert()` (stub)
  - Нет ценности, которую не даёт web CRM
- **Рекомендация:** **Deprecate** операторское ПО. Интегрировать LiveKit-звонки в web CRM.
- **Экономия:** 40-60 часов (не переписывать, а удалить)

**A-Q2. Courier app только для Android**
- **Вопрос:** Почему нет iOS-версии курьерского приложения?
- **Анализ:**
  - iOS занимает ~40% рынка смартфонов
  - Курьеры с iPhone не могут работать
  - Ограничивает найм курьеров
- **Рекомендация:** Добавить iOS-сборку (12-16 часов на настройку + тесты)

**A-Q3. Phone OTP через email**
- **Вопрос:** Почему Phone OTP отправляется на email, а не на телефон?
- **Анализ:**
  - Вводит пользователя в заблуждение (ожидает SMS, получает email)
  - Снижает конверсию на 20-30%
  - `SMS_RU_API_KEY` scaffolded, но не используется
- **Рекомендация:** Интегрировать SMS.ru (16-24 часа)

## 2. Скрытые риски

*Риски, которые не очевидны из `audit.md`, но могут привести к каскадным отказам.*

### 2.1. Каскадные риски

**CR-1. Утечка репозитория → полный компромет production**
- **Триггер:** Утечка `.git` (публичный репозиторий, compromised developer machine)
- **Каскад:**
  1. Злоумышленник получает доступ к 76 Python-скриптам с plaintext-паролем VPS
  2. SSH-доступ к production-серверу (root)
  3. Доступ к `.env.production` с JWT-секретами, `YANDEX_CLIENT_SECRET`, `TELEGRAM_BOT_TOKEN`
  4. Подделка JWT-токенов → доступ к любому аккаунту
  5. Доступ к PostgreSQL → утечка PII (имена, телефоны, адреса, email)
  6. Доступ к FCM credentials → spam push-уведомления
- **Вероятность:** Средняя (если репозиторий приватный, но developer machine compromised)
- **Влияние:** **Катастрофическое** (полная потеря доверия, штрафы 152-ФЗ, судебные иски)
- **Mitigation:** Немедленно удалить хардкод-пароли, перенести секреты в Vault/SOPS, сменить все JWT-секреты

**CR-2. Database corruption → полная потеря данных**
- **Триггер:** Disk failure, ransomware, человеческая ошибка (`DROP TABLE`)
- **Каскад:**
  1. PostgreSQL недоступен
  2. API возвращает 500 на все запросы
  3. Клиенты не могут оформить заказы
  4. Курьеры не видят назначенные заказы
  5. Операторы не могут управлять заказами
  6. Revenue loss: ~50 000₽/день (при 50 заказах × 1000₽)
- **Вероятность:** Низкая (1-2% в год), но влияние катастрофическое
- **Влияние:** **Катастрофическое** (RPO = ∞, RTO = ∞ без backup)
- **Mitigation:** Настроить автоматический backup (8-12 часов)

**CR-3. XSS-атака → кража токенов → массовый компромет аккаунтов**
- **Триггер:** Инъекция JavaScript через user-generated content (например, комментарий к заказу)
- **Каскад:**
  1. Злоумышленник инжектит `<script>` в комментарий
  2. Оператор открывает заказ в CRM → скрипт выполняется
  3. Скрипт крадёт `accessToken` + `refreshToken` из `localStorage`
  4. Злоумышленник получает доступ к аккаунту оператора
  5. Массовая смена статусов заказов, удаление товаров, утечка PII
- **Вероятность:** Средняя (CSP `unsafe-inline` позволяет инъекцию)
- **Влияние:** **Высокое** (компромет CRM, утечка данных)
- **Mitigation:** Nonce-based CSP (16-24 часа), перевести токены в httpOnly cookie (12-16 часов)

**CR-4. DDoS-атака → полный downtime**
- **Триггер:** Злоумышленник отправляет 10 000 RPS на `/api/v1/orders`
- **Каскад:**
  1. Throttler (3/20/100) не справляется (глобальный, не per-IP)
  2. PostgreSQL connection pool (10 connections) исчерпан
  3. API возвращает 429/500 на все запросы
  4. Клиенты не могут оформить заказы
  5. Revenue loss: ~50 000₽/день
- **Вероятность:** Средняя (конкуренты, хактивисты)
- **Влияние:** **Высокое** (downtime, revenue loss)
- **Mitigation:** Per-IP rate-limit (6-8 часов), WAF (8-12 часов), CDN с DDoS protection (12-16 часов)

**CR-5. Платёжный шлюз недоступен → потеря онлайн-заказов**
- **Триггер:** YooKassa/CloudPayments downtime (1-2% в месяц)
- **Каскад:**
  1. Клиент выбирает «Онлайн» оплату
  2. Платёжный шлюз недоступен
  3. Заказ не создаётся (нет webhook'а, нет retry)
  4. Клиент уходит к конкуренту
  5. Revenue loss: ~30% онлайн-заказов (при 2% downtime)
- **Вероятность:** Высокая (платёжные шлюзы часто недоступны)
- **Влияние:** **Среднее** (потеря 30% онлайн-заказов)
- **Mitigation:** Fallback на «Наличные» / «Картой курьеру», retry logic, мониторинг платёжного шлюза

### 2.2. Долгосрочные риски

**LR-1. Технический долг накапливается экспоненциально**
- **Суть:** Текущий техдолг = 580-870 часов. Если не устранять, через 6 месяцев = 1200-1800 часов (из-за каскадных эффектов).
- **Пример:**
  - Нет shared Dart-кода → каждый баг-фикс требует двойной работы → техдолг растёт
  - Нет cron-задач → БД растёт бесконечно → производительность падает → требуется оптимизация
  - Нет APM → невозможно определить bottleneck → производительность деградирует
- **Mitigation:** Выделять 20% времени на техдолг каждый спринт

**LR-2. Зависимость от одного разработчика**
- **Суть:** Команда = 1 разработчик + AI-агенты. Bus factor = 1.
- **Риск:**
  - Разработчик уходит → проект останавливается
  - AI-агенты не могут заменить архитектурные решения
  - Нет code review → качество кода падает
- **Mitigation:** Документация (уже есть), onboarding guide (не создан), hiring plan

**LR-3. Compliance риски (152-ФЗ, GDPR)**
- **Суть:** `UserConsent` реализован, но нет unsubscribe-механизма, нет data retention policy, нет right to be forgotten.
- **Риск:**
  - Штрафы 152-ФЗ: до 6 млн ₽ для юрлиц
  - GDPR: до 4% глобального оборота (если EU-клиенты)
  - Репутационный ущерб
- **Mitigation:** Юридический аудит, data retention policy, unsubscribe механизм

### 2.3. Операционные риски

**OR-1. Нет мониторинга самого мониторинга**
- **Суть:** Grafana/Prometheus/Loki потребляют ресурсы VPS. Если мониторинг падает — никто не узнает.
- **Риск:**
  - Prometheus disk full → метрики теряются
  - Loki OOM → логи теряются
  - Grafana недоступна → операторы не видят дашборды
- **Mitigation:** External uptime monitoring (UptimeRobot, Pingdom), алерты при падении мониторинга

**OR-2. Нет runbook для incident response**
- **Суть:** При инциденте (downtime, утечка данных) нет чёткого плана действий.
- **Риск:**
  - Паника → неправильные решения
  - Долгое время восстановления
  - Репутационный ущерб
- **Mitigation:** Создать runbook (4-6 часов), провести tabletop exercise

**OR-3. Нет on-call rotation**
- **Суть:** Один разработчик = один on-call. Если разработчик недоступен (болезнь, отпуск) — никто не реагирует на инциденты.
- **Риск:**
  - Downtime > 4 часов (RTO нарушен)
  - Revenue loss
  - Репутационный ущерб
- **Mitigation:** Hiring plan, on-call rotation, automated incident response

- PostgreSQL connections: ~8 (из 10 pool)
- CPU usage: ~60%
- Memory usage: ~70%

**Рекомендации:**
- Оптимизировать N+1 запросы (8-12 часов)
- Внедрить Redis caching (12-16 часов)
- Добавить pagination в CRM (12-16 часов)
- Tuning connection pool (2-4 часа)

**Трудозатраты:** 34-48 часов

### 5.3. Сценарий 3: 2000 заказов/день (через 6 месяцев)

- RPS: ~200 (2000 заказов × 10 запросов / 86400 секунд)

- CPU usage: ~90% — **bottleneck**
- Memory usage: ~95% — **bottleneck**

- **SC-C1:** Single-node архитектура → downtime при падении VPS

**Рекомендации:**

- Load balancer (12-16 часов)
- CDN для статики (12-16 часов)
- Email queue (BullMQ) (12-16 часов)
- Vertical scaling (увеличить VPS resources)

**Трудозатраты:** 76-108 часов

### 5.4. Сценарий 4: 10 000 заказов/день (через 12 месяцев)

## 6. Проблемы безопасности

*Attack surface анализ и mitigation strategies.*

### 6.1. Attack surface

**AS-1. Публичные endpoints (без аутентификации)**
- `POST /api/v1/auth/register` (3/min throttle)
- `POST /api/v1/auth/login` (5/min throttle)
- `POST /api/v1/orders` (создание заказа)
- `GET /api/v1/categories`, `/products`, `/promotions`
- `POST /api/v1/auth/social/*` (OAuth)

**Риски:**
- Брутфорс паролей (mitigated: throttle 5/min)
- Брутфорс OTP (mitigated: 10 попыток, но нет exponential backoff)
- DDoS (mitigated: throttle, но глобальный, не per-IP)
- Spam заказов (mitigated: нет, требуется captcha)

**AS-2. Аутентифицированные endpoints (JWT)**
- `GET /api/v1/orders/my` (история заказов)
- `PATCH /api/v1/profile` (обновление профиля)
- `POST /api/v1/mobile/chat/rooms` (создание чата)

**Риски:**
- Кража JWT (mitigated: TTL 15m, но refresh 30d)
- XSS → кража токенов из `localStorage` (mitigated: нет, требуется httpOnly cookie)
- CSRF (mitigated: Content-Type check, но обход через multipart)

**AS-3. Staff endpoints (httpOnly cookie)**
- `GET /api/v1/staff/orders` (заказы)
- `PATCH /api/v1/staff/orders/:id/status` (смена статуса)
- `POST /api/v1/staff/products` (создание товара)

**Риски:**
- CSRF (mitigated: httpOnly cookie, но нет CSRF-токенов)
- XSS → кража refresh-токена из `localStorage` (mitigated: нет, требуется httpOnly cookie для refresh)
- Insider threat (mitigated: нет audit log)

**AS-4. WebSocket endpoints**
- `/staff` (заказы в реальном времени)
- `/orders` (трекинг курьера)
- `/mobile` (уведомления)
- `/chat` (чат)
- `/calls` (звонки)

**Риски:**
- Несанкционированный доступ (mitigated: нет, 3 из 5 gateway'ев без auth)
- WebSocket hijacking (mitigated: нет, CORS `*`)
- DoS (mitigated: нет, нет rate-limit для WebSocket)

**AS-5. Файловые uploads**
- `POST /api/v1/staff/uploads/image` (URL-based)
- `POST /api/v1/staff/uploads/file` (multipart)

**Риски:**
- Загрузка malicious файлов (mitigated: только расширение, не MIME-type)
- SSRF (mitigated: нет, URL-based upload может быть использован для SSRF)
- Disk exhaustion (mitigated: нет, нет quota)

### 6.2. Критические уязвимости

**V-C1. Хардкод-пароли в 76 Python-скриптах**
- **CVSS:** 9.8 (Critical)
- **Attack vector:** Утечка репозитория → SSH-доступ к production
- **Impact:** Полный компромет production
- **Mitigation:** Перенести в `scripts/vps/`, читать из env/SSH key (8-12 часов)

**V-C2. CSP `'unsafe-inline'` для скриптов**
- **CVSS:** 7.5 (High)
- **Attack vector:** XSS через user-generated content
- **Impact:** Кража токенов, сессий, PII
- **Mitigation:** Nonce-based CSP (16-24 часа)

**V-C3. CSRF-проверка только Content-Type**
- **CVSS:** 6.5 (Medium)
- **Attack vector:** CSRF-атака через multipart/form-data
- **Impact:** Несанкционированные действия от имени staff
- **Mitigation:** Origin-check + CSRF-токены (6-8 часов)

**V-C4. Access-токены в localStorage**
- **CVSS:** 7.0 (High)
- **Attack vector:** XSS → кража токенов
- **Impact:** Полный доступ к аккаунту
- **Mitigation:** Перевести в httpOnly cookie (12-16 часов)

**V-C5. WebSocket gateway'и без аутентификации**
- **CVSS:** 8.0 (High)
- **Attack vector:** Подключение к `/staff` без аутентификации
- **Impact:** Утечка заказов в реальном времени
- **Mitigation:** JWT-проверка на connect (8-12 часов)

**V-C6. Брутфорс OTP без exponential backoff**
- **CVSS:** 5.5 (Medium)
- **Attack vector:** Перебор 6-digit кода (10^6 вариантов)
- **Impact:** Несанкционированный доступ к аккаунту
- **Mitigation:** Exponential backoff + IP-based rate-limit (4-6 часов)

**V-C7. `.env.production` может содержать реальные секреты**
- **CVSS:** 9.0 (Critical)
- **Attack vector:** Утечка репозитория
- **Impact:** Компромет всех OAuth-интеграций, подделка JWT
- **Mitigation:** Проверить `.gitignore`, переместить в Vault/SOPS (2-4 часа)

### 6.3. Mitigation roadmap

**Фаза 0 (pre-launch):**
1. Удалить хардкод-пароли (V-C1) — 8-12ч
2. Проверить `.env.production` (V-C7) — 2-4ч
3. OTP brute-force protection (V-C6) — 4-6ч
4. WebSocket auth (V-C5) — 8-12ч

**Фаза 1 (post-launch):**
5. Nonce-based CSP (V-C2) — 16-24ч
6. CSRF origin-check (V-C3) — 6-8ч
7. Access-токены в httpOnly cookie (V-C4) — 12-16ч

**Фаза 2 (1-2 месяца):**
8. 2FA для персонала — 16-24ч
9. Account lockout — 4-6ч
10. MIME-type validation — 4-6ч

**Итого:** 80-120 часов
